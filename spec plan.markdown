## 当前新增：一端发起的设备统一更新（2026-09-10）

用户在尾音修复后明确要求加入统一更新。已实现范围为 Android + Windows x64 接收端和控制台，
新增可选 fleetUpdatesV1 能力，不替换输入协议 v2 或布局 schemaVersion=1。
任一已接入电脑导入发布者签名包并发起请求，前台手机协调缓存、校验、分发和逐设备状态；
也可直接从手机设置发起。先结束听写，再暂停共享麦克风，逐台更新电脑，最后安装手机。
旧电脑先本地安装一次带更新能力的版本；缺少更新接口不能直接远程升级。
离线设备保留补更列表，恢复连接且手机主页在前台时自动重试；安装失败显示原因并允许手动重试。
安卓安装需遵循系统权限和确认，不能将等待确认或取消报告为成功。Mac/iOS 安装尚未实现。
更新包限制固定产物，独立校验发布者签名与哈希；禁止任意路径、URL、远程命令和脚本执行。
电脑使用独立更新进程，保留身份及配置，版本/发布序号/设备身份检查失败则回退；断电恢复仍需本地修复。
详细操作、信任根和清单协议见 docs/FLEET_UPDATES.md，验证事实见 docs/HANDOFF.md 最新记录。

## 当前修复：停止时保护尾音（2026-09-10）

Android dev.15 / Windows dev.9 实现以下收尾语义，不改变 protocol v2/schemaVersion=1：
停止立即关闭手机采音，已采集/排队音频继续传输；发送 HTTP EOF 并等待接收端确认，
网络不可用时在有界预算后退出。共享服务保留网络/CPU 资源至发送收尾。
Windows 在 EOF/取消/上传断开后排空已放行音频，之后供静音 400ms 保护设备尾帧，
再结束本次输出；managed 引擎停止必须等待该阶段。
共享模式手机与 Windows 各限制约 120ms 排队，优先保留最新音频，防止持续积压；
严重网络拥塞时仍可能舍弃旧帧。managed 保留原有 pre-roll 完整顺序。
此修复不拦截共享模式中输入法自己的原生停止键，不承诺输入法停止后仍能接收声音。
自动化、部署和待真机验收证据见 docs/HANDOFF.md 最新记录。

## 0. 面向开源发布的总体规划（2026-09-10）

### 0.1 本轮目标、状态与阅读规则

产品长期定位：**把用户选择的 Android 或 iOS 手机变成 Windows / macOS 电脑的共享麦克风与快捷操作面板，在同一本地网络内自由添加、命名和切换多台电脑，并使用用户选择的语音输入法。**

本轮用户已确认的方向：

- 手机覆盖 Android 与 iOS，电脑覆盖 Windows 与 macOS，允许任意组合。
- 电脑数量不写死为两台、三台或四台，需覆盖 1、2、3、4、5 台及后续扩展。
- 适配 Typeless、微信输入法、豆包输入法、千问输入法等，具有持续增加引擎的能力。
- 提供共享麦克风、快捷键启动、点击麦克风启动、按住说话等可切换的交互。
- 支持多个主题，按开源项目的长期维护和普通用户安装使用要求建设。

**方向已确认；以下技术选型、阶段划分、性能阈值、最低系统版本和工期为建议规划。**
本文不把规划写成已实现，也不把本轮文档修改视为启动所有功能开发。
总体规划建立时的代码基线：Android 1.6.0-dev.14 / Windows 接收端 1.6.0-dev.8 / macOS 预览 2.0.0-dev.3；后续修复版本见文档顶部与交接记录。
通信仍为 v2，Android 布局仍为 schemaVersion=1；本轮没有修改协议或配置实现。

第 0 章是当前总规划。后面的历史变更说明与第 1–22 章保留决策来历和旧版细节；
与本章冲突的旧版本顺序、平台范围、数量上限、主题数量、状态声明和工时估算由本章替代。
最新实测事实记入 docs/HANDOFF.md；实现架构记入 docs/ARCHITECTURE.md。
“规划目标”“代码存在”“构建通过”“真机通过”“正式支持”必须分别记录。

### 0.2 最终用户体验与成功标准

第一次使用的推荐流程：

1. 电脑安装对应平台接收端，选择设备名，如“1号·工作台”，完成需要的系统权限。
2. 手机安装对应 App，点击“添加电脑”，扫描电脑二维码建立信任；不要求打开 USB 调试。
3. 电脑向导检测虚拟音频设备，引导用户安装并选择输入法实际使用的麦克风。
4. 手机显示电脑已连接；用户可先测试快捷键，再主动进行一段语音链路测试。
5. 用户选择“手机控制听写”或“共享麦克风”，界面解释当前会采音、供音、转写到哪里。
6. 添加第 2–5 台电脑时重复扫码即可，每台电脑独立选择输入法和音频输出设备。
7. 手机上切换当前电脑仅改变普通按键/文字目标；共享音频接收范围有独立选择。
8. 关闭后再次启动保留设备、主题和布局；采音是否开始遵循新的会话授权规则。

验收必须包含没有接触过源码的用户从干净系统安装，开发者无需代改 JSON、执行临时脚本或提供个人 data 目录。
建议试用目标：至少 5 位外部测试者中 4 位能仅按文档独立完成首次连接；
外部输入法登录、驱动安装重启所花时间单独记录，不能藏在“扫码即用”的承诺中。

### 0.4 平台、组合与支持等级

| 平台 | 建议产品基线 | 首个支持范围 | 后续范围/条件 |
|---|---|---|---|
| Android | 尽量保留 Android 8/API 26；发布时另定 targetSdk | 同网 Wi-Fi；点击/按住；共享与前台服务；旧 USB 可选保留 | 厂商省电策略逐项验收；蓝牙按键按现状支持等级公布 |
| iOS | 原型暂按 iOS 17+，M0 根据 API 与闲置机覆盖率确定下限 | 原生 App、Wi-Fi、扫码、快捷键、前台采音 | 锁屏持续共享必须真机过门槛；USB/经典蓝牙不列首版承诺 |
| Windows | Windows 11 x64 作为正式测试基线 | 接收端+控制台、WASAPI、受控输入、引擎配置 | Windows ARM64/旧系统按需求与驱动可用性另建矩阵 |
| macOS | 沿用预览 macOS 14.2+ 作为候选下限 | Apple Silicon 先验收，Intel 独立验证后标记支持 | 系统下限随运行时和音频探针实测调整 |

四种手机→电脑组合分别验收：Android→Windows、Android→Mac、iOS→Windows、iOS→Mac。
还须有 Android 和 iOS 各自连接 Windows+Mac 混合组的证据。
“可编译”不等于可输入，“可供音”不等于可控制所有输入法。

支持等级统一为：正式支持 / 预览 / 实验 / 待验证 / 不适用。
操作系统、CPU 架构、输入法版本、音频驱动版本和两种语音模式分别标记。
没有桌面版本或没有所需能力的第三方产品，在对应系统写“不适用/待验证”，不制造适配。

“同一 Wi-Fi”按可互访的本地网络理解，电脑可以通过网线接到同一路由器。
同名 SSID 不保证互通；访客隔离、VLAN、防火墙阻断应能诊断，手动地址也不能绕过网络隔离。

### 0.5 推荐架构与代码边界

建议采用“统一协议和行为模型，平台原生音频/输入/生命周期”的结构：

```text
Android App                         iOS App
采音 / 权限 / 界面                  采音 / 权限 / 界面
           \                         /
           设备目录、目标选择、会话和配置契约
                         |
            发现与安全配对 / HTTPS 控制与音频
                         |
                接收端公共协议与会话核心
                  /                  \
Windows：SendInput/WASAPI       macOS：CGEvent/AUHAL
                  \                  /
              每台电脑的虚拟麦克风
                         |
              本机选择的第三方语音输入法
```

| 层 | 负责内容 | 建议演进 |
|---|---|---|
| 协议契约 | 能力、身份、请求/响应、错误、音频格式、事件、配置 schema | 建立 contracts/ 与跨语言测试样例，先定行为再抽公共库 |
| 设备与配对 | 发现、信任、凭据、在线状态、端点缓存 | 去除固定 IP、电脑数量与开发机路径假设 |
| 会话协调 | 采音所有者、音频订阅、听写目标、租约、取消、恢复 | 单一状态源，手机与电脑用确认/事件更新界面 |
| 音频 | 采集、格式转换、队列、输出、时延计数 | 原生实现，保留 48 kHz PCM16 mono 兼容基线 |
| 引擎适配 | 产品识别、输入设备设置读取、触发、状态探测 | 声明式档案 + 受审查的编译期适配器 |
| 平台输入 | 语义键、真实键位、按下释放、权限 | PRIMARY 与真实 Control/Command 分开 |
| 表现与配置 | 手机底部语音栏、桌面状态、主题、无障碍 | 共享设计令牌、schema 和用例，允许平台导航习惯不同 |

Android 保留 Java，按设备、会话、设置逐步从大型 Activity 拆分，不整体重写。
iOS 建议 Swift + SwiftUI + AVAudioEngine/AVAudioSession；网络、音频会话与视图独立。
Windows 保留 .NET/WPF；macOS 保留现有 .NET 接收端，先补最小菜单栏管理与权限向导，
如采用 SwiftUI 外壳，通过受约束的本地 IPC 管理接收端，避免第二套业务状态机。
以上是推荐选型，M0 用原型验证；不在同一轮同时重写两端 UI、音频传输和接收端。

Windows/macOS 公共代码先通过契约测试统一，再逐块提取为 Receiver.Core；
输入注入、音频设备和系统权限保留独立后端。暂不引入新的 Rust/C++ 跨端核心或微服务体系。
.NET 8 将于 2026-11-10 结束支持；建议在公开稳定版前验证迁移到 .NET 10 LTS，
同时复核 macOS 最低版本、NAudio 和打包兼容性。[S5]

### 0.6 多设备模型、路由和容量

设备模型分开保存：

- computerId：接收端稳定身份；displayName：用户名称；displayOrder：手机上的编号和顺序。
- clientId：每台手机独立身份；pairingId：该手机与该电脑的授权关系。
- endpoints：可变化的 IP/端口/传输；capabilities：当前能力与不可用原因。
- controlTargetId：普通按键、文字、宏的唯一当前目标。
- sharedTargetIds：用户明确选择的共享接收组；不能由“已配对”自动扩大为“能收到音频”。
- sessionId：一次采音会话；每条接收流仍绑定独立电脑身份与授权。
- receiver audio owner：单台接收端当前音频来源手机与会话。

具体规则：

1. 设备目录做成动态集合，禁止在协议或业务代码写死 PC1/PC2/PC3。
2. 第一轮正式容量目标为 **1 台手机、5 台电脑**；同时测 1、2、3、5 台。
   10 台作为压力探索，超过已验证数量显示实验提示，不宣传无限并发。
3. 设备条在 5 台以上可滚动并提供完整列表、搜索、重命名、排序、移除与重新配对。
4. 同名电脑可并存，编号只是标签；接收端重装需建立新信任，IP 变化不能变成新电脑。
5. 当前目标离线后不把操作静默发送给别的电脑，也不缓存快捷键待重连后补发。
6. managed 听写仅一个目标；shared 只共享音频，按键、文字和宏仍只有一个目标。
7. 第二台手机可独立配对；首版同一接收端只允许一个音频源占用，冲突明确拒绝。
   多手机各自操作不同电脑可工作；多人共享输入焦点策略另行定义。
8. 正在 managed 听写时，先停旧会话，再确认新目标；旧端无法确认时关闭旧流并标记未知，
   不自动继续启动新听写。首版建议切换后由用户再次开始；自动交接作为后续增强。
9. shared 模式切换 controlTargetId 不重启采音、不改变 sharedTargetIds；
   加入新共享电脑须用户明确选择，移除则立即关闭该电脑的流。
10. 电脑全离线时不无限采音等待：建议给 15 秒恢复窗口后停止；最终数值经实测调整。

音频原始带宽按 48,000×16×1 = 768 kbit/s/接收端计算；
5 台约 3.84 Mbit/s，另计 TLS/TCP/Wi-Fi 开销。手机应只采集一次，再独立向各端发送。
每端使用有界队列与独立重连退避，慢端不能拖住全部电脑。
不是同步扬声器播放系统，不承诺多电脑采样级同步；各输入法识别结果也不要求一致。

### 0.7 无线发现、首次配对与升级兼容

推荐主流程：电脑开启短时“允许配对”窗口 → 显示二维码 → 手机扫码 →
校验证书身份与一次性配对材料 → 电脑确认手机 → 颁发该手机独立凭据 → 完成能力协商。

设计要求：

- 使用 mDNS/Bonjour 发现指定服务（候选 _phonedeck._tcp），保留旧 Android UDP 发现兼容。
  iOS 优先使用系统 Bonjour；本地网络说明、Bonjour 服务声明与真机权限拒绝/重试必测。[S1]
- 发现只是提供地址，不建立信任。二维码包含身份/证书绑定信息和短时一次性高熵材料，
  不包含永久令牌；成功、取消或过期立即失效，不写日志。
- 手工配对作为相机不可用的辅助流程；短验证码不能直接用作永久密钥。
  推荐采用成熟的 PAKE/带外身份校验方案；具体协议与库在 M1 设计审查中确定，
  未完成认证通道设计前不实现“直接接受任意自签证书后传六位码”。
- 每个 clientId 独立授权，可在电脑撤销某一手机，同时终止该手机现有音频流和控制租约。
  手机删除电脑是本地遗忘，不能宣传为电脑端授权已撤销。
- 证书轮换须通过已信任通道认证；凭据过期、指纹变化、未授权、版本不兼容分开报错。
- QR 配对入口仅开放最小配对操作，短时有效、限速、限尝试次数；输入与音频端点仍强制鉴权。
- Android USB 保留为可选调试/恢复方式，但新增客户端不依赖 USB 信任引导。
- 密钥保存在平台安全存储或受限本地存储；普通布局备份不携带配对秘密。
  部署升级保留原电脑 data；复制安装到另一电脑时不能复制其身份/令牌。

协议与迁移：

1. 先将 v2 现有行为写成契约与测试，再增加可选能力和扩展字段。
2. 每手机授权无法被旧共享令牌完整表达；由明确的新认证版本/能力协商承载，
   不只加 clientId 字段就宣称有客户端隔离。
3. 新接收端允许用户显式开启旧 v2 兼容迁移窗口；列出旧授权的风险与迁移状态，
   窗口关闭后拒绝旧令牌。兼容边界和停止支持版本随发布清单公布。
4. 新手机连旧电脑仅使用旧端声明的能力，并引导升级；不自动降级为未鉴权连接。
5. 状态事件建议采用已鉴权 WebSocket，携带 sessionId、递增状态版本和时间；
   断线后重读完整快照，保留健康轮询回退。旧事件不能覆盖新会话状态。
6. 控制、音频协议版本与各 App 版本分别管理；破坏性变更必须有迁移与回退说明。

### 0.8 麦克风工作模式、触发和状态

**工作模式、触发方式、引擎触发机制是三个不同设置。**

| 用户工作模式 | 手机是否采音/供音 | 谁触发转写 | 停止语义 |
|---|---|---|---|
| 手机控制听写 managed | 会话开始后采音，只供当前目标 | PhoneDeck 调用该电脑引擎适配器 | 立即停本地采集，有界排空已采音频，再结束本次引擎会话 |
| 共享麦克风 shared | 用户启动后持续采音，供已选择电脑 | 每台电脑自己的输入法快捷键或输入法麦克风按钮 | 只关闭供音；不替用户切换输入法，不把“停止转写”当成“停止共享” |
| 关闭 | 无采音、无音频流 | 无 | 撤销当前采音许可和会话，释放资源 |

触发入口：

- 手机点击：一次开始、再次停止；启动中点击取消。
- 手机按住：按下开始，松开、触摸取消、来电或视图退出按同一停止路径处理。
- 电脑 PhoneDeck 快捷键或控制台麦克风按钮：请求供音或请求 managed 会话，
  发往已选择手机并受手机授权/可达状态约束；电脑按钮等待确认，不伪装为麦克风已打开。
- 电脑输入法自己的快捷键/麦克风按钮：在共享模式下直接转写已送达的音频，
  不能假设这个动作天然会唤醒已停止或被杀掉的手机 App。
- 引擎内部 toggle/hold 由适配器转换：手机点击也可以映射为引擎按下保持；
  手机按住也可以映射为引擎开始/停止两次切换，不让用户被两套术语混淆。
- PhoneDeck 供音热键与输入法热键分别配置、检查冲突；同一物理按键不得重复注入形成循环。

界面至少分别展示：

| 状态轴 | 推荐显示 |
|---|---|
| 连接 | 离线 / 连接中 / 已鉴权 / 需重新配对 |
| 手机采音 | 未开启 / 启动中 / 正在采音 / 已中断 |
| 电脑供音 | 未就绪 / 缓冲中 / 正在供音 / 已断开 |
| 引擎转写 | 未运行 / 空闲 / 正在听写 / 无法确认 |
| 目标范围 | 快捷键当前电脑；共享已选择数量与实际供音数量 |

示例：“正在向 3/5 台电脑供音；1号正在听写；2号状态未知”。
采音音量条仅证明手机有声音；供音计数证明送达音频后端；
引擎进程有录音会话不证明文字已生成。端到端自检仍需实际输入验证。

建议统一会话状态：idle → requesting → starting → active → stopping → idle；
任何阶段可进入 interrupted/error，超时后结束本地资源并保留错误原因。
停止优先于启动重试，旧 sessionId 不得复活，按住式快捷键需心跳租约和异常释放。
shared/managed 转换必须结束原模式并确认资源释放，不在同一采音会话中偷换语义。

授权与远程启动建议：

1. 首次远程启动默认关闭；用户可在手机明确允许指定电脑在当前使用会话请求启动。
2. 保存设备授权与保存“正在录音”分开，允许记住偏好，不持久化活动会话。
3. 手机明确点击停止后，旧 sharedRequested=true 不得重新开麦；
   重新开始必须是新的、未过期、经授权请求。
4. 远程请求含 requestId、目标 clientId、有效期和会话代次；接收端重启时不能复活旧请求。
5. App/手机重启、强制结束和权限撤回后默认不采音；受系统限制无法后台启动时显示
   “请在手机打开 PhoneDeck”，不保证远程冷启动。
6. 前台开始的持续共享与“从后台新开麦”分开验收。iOS 锁屏延续录音要配置正确音频会话/
   后台模式，且会被系统事件打断；Android 新开 microphone 前台服务同样受后台限制。[S2][S3]
7. 现有电脑联动功能按此模型迁移，迁移发布说明必须明确行为变化，不能暗中改变现有用户体验。

### 0.9 语音输入法适配体系

目标是“持续扩展、可验证的兼容体系”，每个产品逐项适配，不承诺所有版本天然兼容。

| 目标产品 | 本仓库当前情况 | 下一步 |
|---|---|---|
| Typeless | 已有档案及 Windows 使用证据；Mac 尚待真机 | 建立 Windows/Mac 的独立基准，回归开始/停止、输入设备和探针 |
| 微信输入法 | wetype 实验档案，无默认快捷键 | 真机核实两个桌面平台可用版本、触发和设备选择；与微信聊天客户端区分 |
| 豆包输入法 | 已有 doubao 实验档案，但命名不能证明指向同一产品 | 核对产品/安装包/进程；必要时为输入法新增独立 id，不覆盖原豆包应用 |
| 千问输入法 | 文档示例，未内置验证 | 区分独立输入法与千问桌面应用的语音能力，按系统验证后建立独立档案 |
| 后续输入法 | 未承诺 | 通过统一模板、测试清单和维护人加入 |

官方产品入口见 [S7]–[S10]。网页只用于辨认产品与分发入口，
无法据此断言全局快捷键可注入、虚拟麦克风可选或状态探针可靠。
微信官网本轮访问失败，千问官网正文未成功展开，不能把检索摘要替代真机证据。

适配分级按“产品+系统+版本”分别公布：

- A：受控听写认证。供音、正确输入设备、开始/停止、状态探针和异常释放全部通过。
- B：共享麦克风认证。可接收虚拟音频，由用户在输入法中操作；不承诺自动控制。
- C：实验档案。已描述快捷键/进程等，但未完整验收，用户需手动配置。
- U：待验证或当前不支持，说明具体缺失能力。

“支持共享麦克风”不要求输入法具有可注入快捷键和可靠探针；
“A 级自动控制”才需要完整启动/停止与可信状态机制。
探针未知时显示 unknown，不当成已停止；未具备可靠控制的引擎回退 B 级。
无法读取输入设备配置时，先由向导做人工自检，不能把 null 自动当成配置正确。

引擎档案后续 schema 建议包括：
产品 id、平台、版本范围、可用模式、toggle/hold、快捷键来源、进程/应用标识、
音频设备约束、探针类型、兼容等级、最近验证日期与维护人。
当前 JSON 扩展须向后兼容；不要把未经验证的字段写进已发布协议。

扩展边界：普通贡献用 JSON 声明受控能力；特殊适配通过代码审查后编译进入接收端。
不运行从网络下载的脚本、不从档案自动执行 shell、不依赖坐标点击作为正式控制路径。
第三方更新导致失败时可回退到共享模式，不让一个引擎阻塞整个平台使用。

### 0.10 iOS 专项验证与交付

M0 即做小原型，不等 Mac 全部做完才发现 iOS 限制：

1. 真实 iPhone 申请麦克风/本地网络权限，输出音量与不落盘的 PCM。
2. 经固定证书的 TLS 向 Windows 和 Mac 分别发送音频，验证流式发送和背压。
3. 前台开始后锁屏持续 30 分钟；记录断流、延迟、耗电、温度和系统中断。
4. 来电、Siri、耳机插拔、权限拒绝、网络断开、系统终止分别测试。
5. 验证取消与停止会真正释放麦克风；确认后台不能完成的启动路径如何提示。
6. 验证 Bonjour 权限和扫码相机拒绝后的手工配对路径。

候选实现 AVAudioEngine 采样率不应被假定为固定 48 kHz；
读取实际格式，在内存中确定性转换为协议格式。麦克风输入路径先支持内置麦克风，
蓝牙耳机等路由独立标记能力和音质，不随系统路由变化静默改变承诺。

iOS 不复用 adb reverse；Android RFCOMM 也不能直接作为 iOS 等价实现。
Apple External Accessory 涉及专用配件/MFi 路径，因此首版以 Wi-Fi 为共同连接方式，
有线与蓝牙另做可行性评估。[S4]

交付分成：开发签名真机 → TestFlight 预览 → App Store 稳定分发 + 源码自建说明。
TestFlight 不是长期正式安装方案；上架需要真实后台音频用途、权限说明和清晰录音提示，
不能用播放静音等手段伪装保活。[S6]
Apple 开发者账号、可用 Mac/Xcode、至少两代 iPhone 是完整交付依赖。
最低系统版本和商店材料在发布时再次核实，不在今天冻结未来审核规则。

### 0.11 Windows/macOS 安装、音频与日常管理

Windows 与 Mac 都应提供：

- 开机登录启动开关、单实例接收端、当前手机、供音状态、输入法选择、权限与设备诊断。
- 添加/撤销手机、显示扫码、音频设备选择、热键设置、查看更新与脱敏诊断。
- 自检按“手机采音 → 网络 → 接收端 → 虚拟麦克风 → 输入法 → 测试文本”逐步定位。
- 缺驱动只禁用语音，快捷键仍可用；缺输入权限不影响纯共享供音。
- 输入注入在用户桌面会话运行；锁屏、登录界面和更高权限窗口不列为普通键盘控制承诺。
- 空闲资源与托盘行为有基线，设备缺失/驱动更新/系统睡眠均有恢复流程。

近期继续采用 Windows VB-CABLE、Mac BlackHole；
用户独立安装，PhoneDeck 引导并检查，不擅自改系统默认输入/输出。
若输入法只能使用默认输入设备，由用户明确选择是否修改，并记录恢复方式。
自研“PhoneDeck 虚拟麦克风”作为后续独立研究，需要驱动、签名、系统升级和维护预算，
不成为第一轮四端完成的前置工作；第三方驱动再分发许可须单独核实。

2026-09-14 用户追加明确要求：下线原九套经典主题，只保留简洁浅/深两套。

后续采用统一语义设计令牌：背景、卡片、正文、次级文字、强调、录音、错误、离线、
圆角、间距、字号、触摸区域、动效时长。平台分别渲染，主题 schema 独立版本管理。

8. 主题扩展仅声明式 token/受限资源；首版不提供可执行脚本主题或在线市场。

设置模块建议演进为：电脑与连接、语音输入、快捷键与布局、外观主题、诊断与关于。
保持模块入口与摘要，不回到全部设置平铺长页。

### 0.13 配置归属、升级和隐私

- 手机保存布局、主题、设备别名/顺序；电脑保存引擎、音频设备、本机热键与批准目标。
- 配对秘密独立于可分享配置。主题/按钮导入不授予新电脑信任、不启动录音。
- 新配置用版本、原子写入、校验和迁移备份；未知未来版本拒绝覆盖原文件。
- Android 与 iOS 共享布局/主题 JSON 契约；优先手动导入导出，再做局域网显式同步。
- 电脑 Agent 指令同步保留为有来源的覆盖层；用户覆盖优先级和冲突预览需明确，
  避免远端更新悄悄抹掉手机自定义。
- 自动云同步、账户体系、跨互联网音频中继暂缓。
- PhoneDeck 默认音频不落盘，诊断默认只含状态/耗时/错误码，不含按键正文、令牌和录音。
  如用户主动做录音诊断，单独开启、说明保存位置并可删除。
- “PhoneDeck 在局域网传音”不代表“语音识别完全离线”；第三方输入法可能使用云服务，
  首次选择引擎时告知数据去向取决于该软件，不承诺替第三方控制留存。
- 更新保留身份与用户配置；回退使用兼容备份，不能把更高 schema 直接交给旧程序写回。

### 0.15 分阶段路线与退出条件

使用 M0–M5 作为工作里程碑，与当前三个端不一致的 dev 版本号解耦。

### 0.16 验收矩阵与量化指标

下表为建议目标，M0 建立实际基线后冻结测试方法；
不能用不同硬件/网络的一次测量宣称所有用户都达到该数值。

| 测试项 | 发布门槛建议 |
|---|---|
| 快捷键确认 | 健康本地网络，100 次操作 p95 ≤200 ms；记录手机发出到接收端 ACK，另测真实输入效果 |
| 音频输送 | 热连接手机 PCM 采集到虚拟输出 p95 ≤250 ms；先用可校准方法测，不含第三方云识别 |
| 启动/停止 | 热启动首批有效音频 p95 ≤1 秒；停止本地采音 p95 ≤200 ms；冷启动及引擎就绪单独统计 |
| 超时 | 启动保留当前 6 秒看门狗基线；超时必复位，本地停止不等待网络；停止尾音排空有界 |
| 网络恢复 | 网络重新可达且授权会话仍有效后，建议 10 秒内恢复共享；用户已停止/已重启不自动恢复 |
| 目标隔离 | 1,000 次自动化目标路由测试零串台；各真机组合至少 100 次输入/切换无误发 |
| 模式与异常 | 每组合 100 轮开始/取消/停止；至少 20 轮各阶段断网、睡眠、接收端重启，无挂键/残留会话 |
| 多设备 | 1/2/3/5 台，五台中包含 Windows 与 Mac；慢端、离线端和授权撤销不拖住其他端 |
| 长期共享 | Android/iOS 各两小时锁屏；桌面和混合组八小时运行；检查音频漂移、断流、恢复与热量 |
| 音质 | 固定中文/英文/数字文本，与同输入法直接虚拟麦克风基准对比；首尾音节不系统性丢失 |
| 状态真实 | 手机采音、后端供音、引擎探针分别核对；未知/中断不得显示成功或已停止 |
| 资源 | 记录 1/3/5 台 CPU、内存、线程、带宽、耗电和温度；预热后不持续增长、不长期热降频 |
| 升级 | 原身份/配对/自定义布局/主题保留；旧/新手机接收端组合按协商工作；失败可恢复兼容备份 |
| 无障碍 | 九主题关键状态、字体放大、读屏、取消手势和系统减弱动态效果均可操作 |
| 安全 | 未授权/过期/错误目标/重放/撤销后请求被拒绝；导出包与日志没有秘密和默认录音 |

多设备下不把 sharedTargetIds 中未就绪设备计为供音成功；
跨主机时间测量需同步/校准，不能直接相减未经同步的系统时钟。

兼容测试策略控制组合爆炸：

- 四种手机→桌面组合与各平台生命周期是必须全测的基础链路。
- 引擎在桌面按“产品×平台×版本×toggle/hold×探针能力”认证。
- 各手机端使用契约测试覆盖所有引擎描述，再选代表性 A/B/hold 引擎做端到端交叉验证。
- 新引擎不要求重新测全部主题，但状态 schema 变化必须触发 UI 状态回归。
- 所有报告记录日期、commit、构建版本、设备/OS、输入法/驱动版本、步骤和证据。
  虚拟机/模拟器/真机结果分列。

## 历史规格与决策记录（阅读当前路线时以第 0 章为准）

## 变更说明（2026-09-03：双语音模式与共享麦克风）

1. 保留并互斥切换两套工作方式：`managed` 手机控制听写仍只面向当前电脑；`shared`
   共享麦克风把同一次采音供给所有在线且声明 `sharedMicrophone`、虚拟音频就绪的电脑。
2. 共享模式不替用户触发、停止或复位 Typeless；每台电脑继续使用本机快捷键，所以允许
   两台或三台同时转写。手机“当前电脑”仍只控制快捷键、文字和宏的发送目标。
3. Android 共享运行状态不持久化，每次 App/手机启动后须手动开启；开启后由 microphone
   前台服务持有单个 48 kHz PCM16 mono AudioRecord、Wi-Fi/CPU 锁及常驻停止通知。
4. 每台接收端拥有独立 500 ms 有界队列和写线程，慢端只丢自己的旧帧；LAN 优先、当前
   USB 回退、蓝牙无音频，掉线端独立退避并在恢复后自动加入。
5. 协议继续为 v2；音频流新增可选 `X-PhoneDeck-Audio-Mode: managed|shared`，缺省
   `managed`。共享流对所有目标使用一个 UUID sessionId，每条连接仍携带自己的目标 ID、
   令牌与证书固定信息。接收端单流独占；冲突 409，虚拟声卡缺失 503。
6. Windows shared 立即写 VB-CABLE 而不操作 Typeless；macOS 14.2+ 通过 AUHAL 定向
   BlackHole 2ch，并使用 Core Audio 进程对象 `isRunningInput` 支撑 managed 状态机。
7. dev.5/dev.2 的源码与自动化已完成；真实三机、Mac 音频、20 轮切换和两小时锁屏共享
   仍是发布前验收项，不能据此提升上一实机稳定基线。

## 2. 产品定义

### 2.1 一句话定位

PhoneDeck 是一个以手机麦克风语音输入为核心、可自定义快捷操作为辅助，并能在多台 Windows / macOS 电脑之间切换输入目标的个人桌面控制台。

### 2.2 产品真正要解决的问题

1. 把闲置 Android 手机转化为长期可用的电脑辅助设备。
2. 利用手机麦克风替代距离较远或音质较差的电脑麦克风。
3. 通过手机一键唤醒或停止 Typeless，降低电脑端语音输入的操作成本。
4. 将高频电脑快捷键做成大尺寸、可识别、可触摸的按钮。
5. 允许用户按自己的软件习惯修改快捷键，而不是被固定布局限制。
6. 在 USB 长期连接场景中提供低延迟、高可靠性的语音和按键操作。
7. 让一台手机管理多台电脑，并通过一次明确操作切换语音与快捷键的目标设备。
8. 在不依赖云账户的前提下兼容直接 USB、USB 硬件切换和本地无线连接。

### 2.3 产品不是什么

1. 不是完整替代实体键盘的全键盘输入法。
2. 不是在手机端完成语音转文字；语音识别仍由电脑端 Typeless 完成。
3. 不是默认开放任意 PowerShell、CMD 或系统命令的远程执行工具。
4. 不是第一阶段就要覆盖 OBS、智能家居、音乐平台等所有插件生态的通用遥控器。
5. 不是依赖云账户才能工作的服务；核心功能应在本地运行。

### 2.4 差异化能力

同类宏面板通常强调自定义按钮和自动化。PhoneDeck 的首要差异是：

1. 手机麦克风以 48 kHz / 16-bit / 单声道 PCM 通过 USB 实时送入 Windows。
2. 和 Typeless 听写状态联动，手机端一个动作同时管理麦克风与 Typeless。
3. USB 与蓝牙双通道：USB 负责音频和按键，蓝牙作为按键备用通道。
4. 底部常驻的大型语音操作区，面向单手、盲操作和长期插线使用。
5. 后续在不牺牲语音体验的前提下，加入可编程快捷键能力。
6. 后续提供多电脑目标选择；手机端保持同一个 App，每台电脑运行各自系统的接收端。

### 3.2 当前固定动作

- 复制、粘贴、剪切；
- 撤销、重做、全选、保存；
- Alt+Tab、任务视图、显示桌面；
- Windows 截图；
- Typeless；
- 切换输入法；
- 回车、退格、删除、Esc、空格；
- 上下左右；
- 音量增加、降低、静音；
- 固定文字输入（电脑端已有基础能力，手机界面暂未开放）。

### 3.3 当前架构限制

1. 手机按钮的名称、位置和动作写死在 `MainActivity` 中。
2. 手机发送的是 `copy`、`screenshot` 等固定动作名称。
3. 电脑端使用固定 `switch` 白名单执行动作。
4. 用户不能把“截屏”改成 F1，也不能新增组合键。
5. 没有配置版本、配置导入导出和升级迁移机制。

9. 手机端只保存一个 USB 目标和一个蓝牙连接，没有电脑设备列表、稳定设备 ID 或当前目标概念。
10. 电脑端只描述本机服务是否正常，没有跨电脑发现、配对、身份验证和状态同步。
11. Windows 与 macOS 尚未抽象为统一输入和音频后端。

## 4. 总体产品原则

### 4.1 语音优先

无论增加多少快捷功能，底部语音按钮都必须保持快速、稳定、容易触达。快捷键功能不能挤占或破坏语音主入口。

点击模式必须用同一主按钮明确表达开始、启动中取消和停止，不再显示独立暂停/继续按钮；
停止操作必须先关闭本地采集，再等待电脑端确认，不能因网络收尾让用户感觉仍在录音。
手机不得仅因 USB 健康检查成功就启动听写；必须同时确认虚拟音频播放端存在且 Typeless 已选中对应的 `CABLE Output`。服务端的“已停止”必须尽可能与 Windows Core Audio 中 Typeless 的真实录音会话核对，不能只清除内存标志。

### 4.2 设置简单

普通用户不应该理解虚拟键码、扫描码或 JSON。设置界面应使用“F1”“Ctrl + Shift + S”这样的自然显示方式。

### 4.3 可恢复

任何按钮都可以恢复默认。配置损坏时 App 必须回退到可用的默认布局，不能导致主界面无法启动。

### 4.4 本地优先

配置、音频和按键指令默认只在手机与当前电脑之间传输，不要求登录云账户。

### 4.5 安全边界明确

可自定义不等于执行任意代码。电脑端必须验证动作类型、按键数量、文本长度、步骤数量和延迟范围。

### 4.6 有反馈

所有触发必须明确显示：正在发送、电脑已确认、执行失败。需要电脑状态的按钮不能只在手机本地假装成功。

### 4.7 渐进升级

先做好单按键和组合键，再做宏、自动配置和插件；避免第一版自定义系统过度复杂。

### 4.8 目标必须明确

多电脑环境中，手机主界面必须始终清楚显示当前输入目标。除非用户主动选择广播动作，否则语音、快捷键和文字只允许发送给一台明确选中的电脑。主界面的编号切换按钮固定放在语音面板右下方，顶部连接卡继续显示当前电脑全名。

### 4.9 传输方式可替换

手机配置、按钮动作和电脑身份不得绑定某一种连接方式。USB、USB 共享切换器、局域网和蓝牙只是传输层；上层统一使用电脑 ID、会话 ID、能力协商、请求确认和去重。

## 7. 配置数据设计

### 7.1 建议的配置归属

已确认 1.5.0 以手机本地配置为快捷键布局的主要数据源：

- 手机需要离线渲染按钮；
- 设置页面就在手机上；
- USB 与蓝牙都可以发送相同的结构化动作；

- 验证动作是否合法；
- 把结构化按键转换为 Windows 输入；

程序路径、文件夹路径等电脑专属数据在 1.7.0 再设计电脑端配置同步。

### 7.2 建议的数据结构

1.5.0 仍保留 `profiles` 外层结构，但手机界面只显示一个 `default` / “通用”配置。这样 1.7.0 增加多配置时不需要再次重构和迁移整个数据格式。

```json
{

      "id": "default",

      "columns": 3,
      "buttons": [
        {
          "id": "agentPlan",

          "icon": "",

          "sortIndex": 0,

          "action": {
            "type": "text",
            "text": "/plan",
            "submit": true
          }
        }
      ]
    }
  ]
}
```

### 7.3 存储要求

1. 使用 Android 应用私有存储。
2. 写入时使用临时文件或等价的原子写入方式，避免中途损坏。
3. 每次读取先检查 `schemaVersion`。
4. 解析失败时保留损坏文件副本，并自动加载默认配置。
5. 不将 Android 权限状态写入快捷键配置。
6. 不在配置中保存签名私钥、ADB 密钥或敏感令牌。

### 7.4 配置迁移

1. 1.4.0 升级至 1.5.0 时自动生成与当前布局一致的默认配置。
2. 保留用户已经选择的语音模式。
3. 后续增加字段时必须提供默认值。
4. 不认识的未来配置版本不能直接覆盖，应提示版本不兼容。

### 7.5 导入导出（建议 1.5.x）

1. 导出为可读 JSON 文件。
2. 导入前验证版本、字段、动作类型和大小限制。
3. 导入前展示配置名称、按钮数量和来源文件。
4. 导入时允许“覆盖当前”或“另存为新配置”。
5. 任何程序路径或敏感文本应在导出前明确提示。

实现状态（2026-08-26）：协议 v2 基础已进入 1.5.0 候选源码。Windows 接收端生成稳定
`computerId`，健康检查返回平台、架构和能力；`keyChord` 请求必须携带 v2 信封并匹配

### 8.1 兼容原则

3. 手机与电脑端在健康检查中交换协议版本。
4. 如果电脑端版本过旧，手机应提示“电脑端需要更新”，不能静默失败。

```json
{
  "ok": true,
  "name": "PhoneDeck",
  "version": "1.5.0",
  "protocolVersion": 2,
  "computerId": "UUID",
  "displayName": "工作台",
  "platform": "windows",
  "architecture": "x64",
  "capabilities": [
    "fixedAction",
    "keyChord",
    "text",
    "phoneAudio"
  ],
  "audio": {
    "available": true,
    "device": "CABLE Input (VB-Audio Virtual Cable)"
  }
}
```

### 8.3 新按键请求建议

```json
{
  "protocolVersion": 2,
  "requestId": "UUID",
  "sessionId": "UUID",
  "targetComputerId": "UUID",
  "action": "keyChord",
  "keys": ["CTRL", "SHIFT", "S"],
  "holdMs": 45
}
```

### 8.4 电脑端验证规则

1. `requestId` 必须存在且长度受限。
2. `action` 必须在允许的动作类型中。
3. `keys` 只能使用内置按键名称映射表。
4. 单次组合最多 4 个键。
5. 不允许重复键。
6. `holdMs` 采用安全范围，例如 20–500 毫秒。
7. 文本输入需要设置长度上限。
8. 宏步骤数量和总执行时间必须受限。
9. USB、局域网与蓝牙共用相同的动作验证和去重逻辑。
10. 多电脑请求必须验证 `targetComputerId` 与本机身份相同，不能接受发给其他电脑的动作。
11. 会话型动作必须验证 `sessionId`，过期语音会话不能恢复或接管新会话。
12. 返回结果必须包含 `requestId`、成功状态、是否重复、实际电脑 ID 和错误信息。

### 8.5 响应建议

```json
{
  "requestId": "UUID",
  "ok": true,
  "duplicate": false,
  "computerId": "UUID",
  "message": "已发送 F1"
}
```

### 8.6 Windows 输入注意事项

1. 使用 `SendInput` 发送按下和松开事件。
2. 修饰键先按下、普通键后按下；松开时顺序反转。
3. 出现异常时必须尽力释放本次已经按下的键。
4. Windows UIPI 会阻止低权限程序向更高权限程序注入输入。
5. 若目标程序以管理员身份运行，而 PhoneDeck 电脑端没有相同权限，应给出明确提示或说明。
6. 不建议默认让 PhoneDeck 以管理员身份长期运行。

## 9. PhoneDeck 1.6.0：多电脑切换中心

### 9.1 功能结论与目标

状态：`已确认方向`。多电脑支持提升为 PhoneDeck 的核心产品能力，优先级高于继续增加固定按钮。

目标场景：一台 Android 手机同时管理两至四台电脑，电脑可以是 Windows 与 macOS 的任意组合。用户在手机上选择一台当前目标后，语音、快捷键、文字和后续宏动作都发送到该电脑。

第一阶段不做默认广播。任意时刻只能有一台“当前输入目标”，从而避免语音或按键误发到其他电脑。

### 9.2 连接方式评估

| 方案 | 是否能同时保持多电脑在线 | 手机音频 | 切换方式 | 优点 | 限制 | 定位 |
|---|---:|---:|---|---|---|---|
| 手机直接 USB | 否 | 支持 | 重新插线 | 延迟低、链路简单 | 一次只能连接一台主机 | 单机与故障备用 |
| 普通 USB Hub / 一分多线 | 否 | 不适用 | 不可用 | 可让一台主机接多个外设 | 不能让一个手机同时连接多台主机；不应使用多主机 Y 线 | 明确排除 |
| 多电脑 USB 共享切换器 | 否，只有被选中的主机取得 USB 控制权 | 支持，待实机验证 | 实体按钮或外置切换键 | 不依赖局域网；可兼容 Windows / Mac；无需改造音频编码 | 每次切换等同 USB 拔插；ADB 隧道会重建；手机无法天然知道硬件当前端口 | 可选硬件模式 |
| 同一 Wi-Fi / 手机热点 | 是 | 支持 | 手机软件内一键切换 | 三台电脑都可显示在线；无需拔插；最符合目标 UX | 需要接收端监听局域网、配对鉴权和防火墙配置 | 推荐主模式 |
| 经典蓝牙 RFCOMM | 理论上可多连接，当前实现仅一台 | 当前不支持 | 手机软件切换 | 不依赖路由器 | 多系统兼容和多连接稳定性较差；高质量实时音频改造大 | 快捷键备用 |
| USB over IP 设备服务器 | 通常仍是一台客户端独占 | 取决于设备与驱动 | 厂商软件切换 | 可跨距离共享 USB | 成本、驱动、手机兼容性和 macOS 支持不确定 | 暂不采用 |

USB 采用主机控制的点对点拓扑。普通 Hub 的方向是“一台主机扩展多个设备”，不能反向把一个 Android USB 设备并联给三台主机。任何宣称简单一分三的数据线都不作为 PhoneDeck 支持方案，以避免多主机供电冲突、枚举失败或设备损坏风险。

### 9.3 USB 共享切换器硬件模式

可购买的正确品类名称：

- `多电脑 USB 共享切换器`；
- `USB Peripheral Sharing Switch`；
- 三台电脑场景通常购买支持四台电脑的型号；
- 选择带独立外置切换按钮、端口指示灯和辅助供电接口的型号；
- USB 2.0 带宽已经足够 ADB 传输本项目的单声道 PCM，USB 3.x 不是必需条件；
- 必须确认产品的“电脑端口数量”，不能把“4 个 USB 外设口”误认为支持 4 台电脑。

连接示意：

```text
Android 手机
    │
USB 共享切换器
    ├── Windows A
    ├── Windows B
    ├── macOS C
    └── 预留端口
```

硬件模式工作流程：

1. 每台电脑分别安装 PhoneDeck 接收端、ADB 和所需虚拟音频设备。
2. 手机首次切换到每台电脑时，分别完成 USB 调试授权。
3. 每台电脑运行 PhoneDeck 后台监测程序。
4. 用户按共享切换器的实体按钮选择电脑。
5. 新电脑检测到 Android 后自动建立 `adb reverse`、识别手机并唤醒 App。
6. 手机通过健康检查确认当前 USB 连接对应的电脑名称，并自动更新当前目标。
7. 切换过程中如果正在听写，必须先停止旧会话；异常拔断时两端自动清理残留音频状态。

硬件模式限制：

1. 三台电脑并非同时连接，只有一个 USB 端口具有焦点。
2. 无法只靠手机 App 控制普通机械切换器；用户仍要按硬件按钮。若要由手机控制硬件，需另选具有开放控制接口的切换器，复杂度和成本都会上升。
3. 每次切换都会触发 USB 断开和重新枚举，预计恢复时间高于局域网软件切换。
4. 手机供电取决于切换器设计。应选择带辅助供电的正规型号并实测持续充电、数据连接和温度。
5. macOS 端仍需要单独的 PhoneDeck 接收端、ADB、虚拟音频配置和系统权限；硬件不会消除软件适配工作。
6. 购买前不能承诺具体手机兼容，必须使用当前 Samsung 手机、真实线材和目标电脑做样机验收。

### 9.4 推荐的混合架构

最终架构不在“只用局域网”和“只用硬件”之间二选一，而是让目标设备独立于传输方式：

```text
手机端 Device Manager
    ├── 当前 USB 电脑：ADB reverse
    ├── Windows A：本地网络会话
    ├── Windows B：本地网络会话
    ├── macOS C：本地网络会话
    └── 蓝牙：按键故障备用
```

推荐默认顺序：

1. 已配对且在线的局域网连接；
2. 当前直接 USB 或 USB 共享切换器连接；
3. 已配对蓝牙快捷键连接；
4. 不自动通过互联网中转。

用户可以只使用 USB 共享切换器，不强制启用局域网；但若希望三台电脑同时显示在线，并在手机上真正一键选择目标，则必须使用局域网、手机热点或未来其他多点无线通道。

### 9.5 手机端设备与目标 UX

主界面顶部固定显示：

```text
当前电脑：工作台 Windows  ● 在线
[切换电脑]  [设备列表]
```

交互要求：

1. 单击“切换电脑”在在线且已配对的电脑间循环切换。
2. 长按或点击当前电脑名称打开完整设备列表。
3. 设备卡片显示：自定义名称、Windows / macOS、在线状态、连接方式、Typeless 状态、虚拟麦克风状态和最近延迟。
4. 切换成功后提供震动、颜色和目标电脑确认。
5. 离线电脑不可被误选；允许显示“尝试重新连接”。
6. 用户可以调整循环切换顺序并指定默认电脑。
7. 手机重启后记住上次目标，但必须重新确认该电脑在线，不能在未确认时发送动作。
8. USB 共享切换器换端口后，手机自动采用新 USB 主机报告的电脑身份。
9. 目标切换和“快捷键配置页面切换”是两个不同概念，界面文案必须避免混淆。

### 9.6 语音切换规则

空闲时切换目标：立即切换，不启动 Typeless。

正在听写时切换目标，采用受控交接：

1. 向旧电脑发送停止听写并等待确认。
2. 关闭旧电脑音频流并释放手机麦克风会话。
3. 将新电脑设为当前目标。
4. 检查新电脑的虚拟音频与 Typeless 是否可用。
5. 建立新电脑音频流。
6. 唤醒新电脑 Typeless。
7. 显示“已切换，可继续说话”。

要求：

- 切换期间显示明确的“正在切换”，不假装连续无缝。
- 第一版允许约 0.5–1.5 秒停顿，用户应在看到成功提示后继续讲话。
- 已经输入到旧电脑的文字不会自动搬到新电脑。
- 旧电脑没有确认停止时，优先确保关闭旧音频流，再提示用户检查旧电脑 Typeless 状态。
- 后续可研究短时本地音频缓冲，但不得默认保存完整录音。
- 上述单目标限制只适用于 `managed`；用户明确选择并手动开启 `shared` 后，同一采音会话
  可向全部合格电脑扇出，但共享模式自身不得操作任何一台 Typeless。

### 9.7 电脑身份、发现与配对

每个接收端首次启动时生成稳定身份：

```json
{
  "computerId": "随机 UUID",
  "displayName": "工作台",
  "platform": "windows",
  "architecture": "x64",
  "instancePublicKey": "...",
  "capabilities": ["keyChord", "text", "phoneAudio", "typeless"]
}
```

局域网模式：

1. 使用 mDNS / Bonjour 或等价机制发现接收端。
2. 首次连接由电脑显示二维码或六位验证码，用户在手机确认。
3. 配对后保存电脑 ID 和连接密钥，不依赖可能变化的局域网 IP。
4. 每台电脑可在电脑端撤销手机授权；手机也可删除电脑。
5. 企业或访客网络可能阻止设备互访，应支持手动输入地址和手机热点模式。
6. Windows 防火墙和 macOS 防火墙需要首次运行引导。

### 9.8 协议与接收端重构

协议 v2 必须提前预留以下字段：

```json
{
  "protocolVersion": 2,
  "requestId": "UUID",
  "sessionId": "UUID",
  "targetComputerId": "UUID",
  "action": "keyChord",
  "keys": ["PRIMARY", "C"]
}
```

其中 `PRIMARY` 根据目标平台映射：

- Windows：`CTRL`；
- macOS：`COMMAND`。

接收端拆分为统一服务层与平台后端：

```text
PhoneDeck Receiver Core
    ├── 身份、配对、协议、心跳、去重
    ├── Windows Input：SendInput
    ├── Windows Audio：WASAPI → VB-CABLE
    ├── macOS Input：CGEvent
    └── macOS Audio：Core Audio → 虚拟音频设备
```

健康检查需要增加：电脑 ID、名称、系统、架构、协议版本、接收端版本、Typeless 状态、音频设备状态、当前会话和能力列表。

### 9.9 安全与隐私

当前 USB 服务只监听 `127.0.0.1`。一旦开放局域网连接，必须新增：

1. 未配对设备不得发送按键、文字或音频。
2. 请求必须带目标电脑 ID、会话 ID、请求 ID 和消息认证信息。
3. 音频和指令使用配对密钥保护，避免同一网络其他设备监听或伪造。
4. 接收端只开放 PhoneDeck 所需端口和协议，不提供任意命令执行。
5. 电脑端提供“已配对手机”和一键撤销入口。
6. 默认只允许本地网络；不自动暴露到公网。
7. 日志不保存音频、配对密钥、完整快速文字或敏感剪贴板内容。

### 9.10 异常与恢复

必须覆盖：

1. 当前电脑睡眠、关机或离开网络。
2. USB 共享切换器在语音过程中换端口。
3. ADB 设备编号变化、`adb reverse` 被清空或手机撤销授权。
4. 新电脑在线但 Typeless 未运行。
5. Windows / macOS 虚拟音频设备缺失。
6. 同名电脑、IP 地址变化和电脑重装后身份变化。
7. 两个接收端同时声称自己是当前 USB 主机。
8. 手机从 Wi-Fi 切换到移动网络或热点。
9. 切换目标时旧电脑未确认停止。
10. App 被系统杀死后恢复上次设备列表，但不恢复未确认的听写会话。

### 9.11 验收标准

1. 一台手机成功配对三台电脑并显示各自真实在线状态。
2. Windows A → Windows B 切换后，复制和 F1 只作用于 B。
3. Windows → macOS 切换后，逻辑复制自动从 Ctrl+C 映射为 Command+C。
4. 语音空闲时切换不误触发任何一台 Typeless。
5. 语音进行中完成受控交接，旧电脑停止、新电脑开始，状态没有永久卡住。
6. 未配对电脑向接收端发送请求时被拒绝。
7. IP 地址变化后仍能通过电脑 ID 重新发现和连接。
8. USB 共享切换器连续切换 20 次，ADB、端口转发、App 状态和语音均可恢复。
9. 任意一台电脑离线不阻塞其他电脑使用。
10. 手机界面始终明确显示当前目标和连接方式。

### 9.12 分阶段实施与工时

阶段 A：协议与设备身份基础，约 12–20 小时。

- 协议 v2 增加目标、会话、平台和能力字段；
- 接收端稳定电脑 ID；
- 手机设备数据模型；
- 保持 1.4.0 USB 协议兼容。

阶段 B：Windows 多电脑 MVP，约 25–40 小时。

- 同一局域网或手机热点；
- 手动添加或简单发现；
- 两至三台 Windows 在线；
- 空闲状态切换快捷键和语音目标。

阶段 C：Windows 正式版完善，累计约 50–80 小时。

- 安全配对；
- 自动发现；
- 断线重连；
- 完整状态反馈；
- 语音进行中的受控交接；
- 防火墙与首次运行向导。

阶段 D：USB 共享切换器兼容验证，约 8–16 小时，另需购买样机。

- 三或四电脑硬件实测；
- 供电、ADB 授权、自动转发和连续切换；
- Windows / macOS 混合环境测试。

阶段 E：macOS 接收端，额外约 40–70 小时。2.0.0-dev.2 已完成输入、AUHAL/BlackHole、
Typeless managed/shared 源码、构建脚本与自动化测试；真实 Mac 验收、安装向导、签名和
公证仍在该阶段内。

完整 Windows + macOS 多电脑正式版本总量预计约 90–150 小时，具体取决于真实 Mac 硬件、代码签名、公证和 USB 切换器兼容性测试。

### 9.13 当前推荐结论

1. 多电脑功能确定进入正式路线。
2. 普通 USB Hub 或 Y 线不能实现目标，明确不采用。
3. USB 共享切换器可以作为“不使用局域网”的可选方案，但属于一台一台物理切换。
4. 若要求三台电脑同时在线且由手机一键选择，局域网或手机热点仍是最合适的主通道。
5. 采用混合架构，避免以后把手机配置绑定死在 USB 或 Wi-Fi。
6. 在 1.5.0 设计协议 v2 时就加入电脑身份和平台能力字段，避免 1.6.0 再次大改。
7. 进入硬件采购前，先选一台支持四电脑、外置按钮、辅助供电的正规 USB 共享切换器进行概念验证，不一次性购买多台。

## 11. PhoneDeck 1.8.0：宏、文字和启动动作

1.6.0-dev.3 已提前加入受控宏的实验子集：每个宏 1–8 步，仅允许白名单按键或单行文本，
单步前置延迟限制在 0–2000 ms。焦点保障、失败策略、运行中取消和更完整的自动化能力仍按
本章作为 1.8.0 范围，不把实验实现宣称为稳定完成。

### 11.1 多步骤宏

一个按钮按顺序执行多个步骤，例如：

```text
Ctrl+A
等待 100 ms
Ctrl+C
等待 200 ms
打开指定程序
```

建议限制：

- 最多 20 个步骤；
- 单次等待 0–5000 ms；
- 总执行时间不超过 15 秒；
- 同一按钮执行期间禁止重复启动；
- 提供取消按钮；
- 失败后停止还是继续由宏设置决定。

### 11.2 快速文字

用途：

- 邮箱；
- 地址；
- 常用回复；
- 固定提示词；
- 日期时间模板；
- 工作中的标准文本片段。

要求：

1. 默认最大长度，例如 4000 字符。
2. 明确提示文字将输入到当前电脑光标位置。
3. 密码和敏感令牌不建议使用此功能保存。
4. 导出配置时对文字内容进行隐私提醒。

### 11.3 打开程序、网页和文件夹

建议采用电脑端“已批准目标”机制：

1. 电脑端选择程序或文件夹。
2. 电脑端生成稳定目标 ID。
3. 手机按钮只保存目标 ID 和显示名称。
4. 手机不能直接发送任意命令行。
5. 第一次执行新目标时电脑端可要求确认。

不建议：手机直接发送任意 PowerShell、CMD 或脚本内容。

### 11.4 多手势动作

候选能力：

- 单击；
- 长按；
- 双击；
- 按下开始、松开结束；
- 连续按住重复。

风险：手势过多会降低可发现性并增加误操作，因此进入开发前需要单独讨论。

## 13. 语音输入后续优化

### 13.1 可考虑功能

1. 麦克风软件增益。
2. 噪声门阈值。
3. 音量过低和削波提醒。
4. 最大听写时长。
5. 长时间无声音自动停止。
6. 一键音频链路自检。
7. VB-CABLE 不可用时的修复提示。
8. Typeless 未运行时的明确提示。
9. 音频断开时自动停止 Typeless。
10. 语音开始和停止提示音开关。

### 13.2 不应轻易加入的处理

1. 强降噪：可能破坏语音清晰度，应先进行 A/B 测试。
2. 自动增益：可能引入底噪和音量泵动。
3. 手机上再次有损压缩：USB PCM 当前音质良好，没有必要。
4. 云端转码或云端中转：增加延迟和隐私风险。

### 13.3 音频验收指标建议

- 手机正常讲话时音量条持续有变化；
- 无明显爆音、周期性断裂和速度变化；
- 开始听写后尽快出现有效音频；
- 启动过程中点击取消，手机麦克风和电脑会话都能立即回到空闲；
- 再次点击主按钮停止后，Android 系统不再显示麦克风正在运行；
- 停止后不继续占用手机麦克风；
- 连续执行 20 次开始 / 停止无残留状态；
- USB 重插并重新运行启动脚本后可恢复；
- Typeless 识别准确度不低于 1.4.0 基线。

```text
设置

│  ├─ 点击说话 / 按住说话
│  ├─ 提示音与震动
│  └─ 音频自检（后续）

├─ 电脑与连接（1.6.0）
│  ├─ 当前目标电脑
│  ├─ 已配对电脑列表
│  ├─ 添加电脑 / 扫码配对
│  ├─ 设备名称与切换顺序
│  ├─ USB / 局域网 / 蓝牙状态
│  ├─ USB 共享切换器模式
│  └─ 删除电脑与撤销授权
├─ 配置管理（1.7.0）
│  ├─ 当前配置
│  ├─ 新建配置
│  └─ 自动切换
└─ 关于
   ├─ 手机端版本
   ├─ 使用说明
   └─ 隐私与安全
```

### 14.3 无障碍

1. 所有按钮提供内容描述。
2. 状态不能只依靠颜色区分。
3. 字体放大后仍可操作。
4. 关键按钮最小触摸面积不低于 Android 建议值。
5. 拖动排序需要提供不依赖拖动的“上移 / 下移”替代操作。

### 14.4 主题与视觉反馈

1. 手机端提供冰川玻璃、深海蓝、OLED 黑和柔和浅色四套主题，并使用语义颜色令牌，不在页面中重复写死颜色。
2. 冰川玻璃主题使用低成本的本地渐变与半透明卡片；不依赖网络图片，也不要求设备支持实时背景模糊。
3. OLED 主题保持纯黑主背景，适合手机长期亮屏；主题切换不得改变语音模式、快捷键配置或连接状态。
4. 底部语音主按钮在空闲、启动、听写和错误状态必须同时通过文字、颜色、波形或图标表达，不能只依靠颜色。
5. 快捷键卡片必须提供发送中、电脑确认成功和失败反馈；失败后仍可再次点击。
6. 玻璃层透明度必须保证滚动内容不会穿透到底部语音区而影响文字辨认。
7. 冰川背景使用静态自绘光斑，避免持续动画导致长期亮屏时耗电和掉帧。

## 15. 安全与隐私规格

### 15.1 音频

1. 手机音频只在用户主动开始听写后传输。
2. 停止后立即释放麦克风。
3. 默认不保存录音。
4. 电脑端仅向用户已经配置的虚拟音频设备输出。

### 15.2 网络与连接

1. USB HTTP 服务继续仅监听 `127.0.0.1`。
2. 局域网服务使用独立端口和明确防火墙规则，不复用无鉴权的 USB 入口。
3. 局域网请求只接受已经由验证码或二维码配对的手机，并验证消息完整性。
4. 蓝牙连接只接受已配对设备。
5. 请求需要目标电脑 ID、会话 ID、大小限制、超时和异常处理。
6. 动作执行继续使用请求编号去重。
7. 默认不允许互联网入站，不通过云端转发音频。

### 15.3 自定义动作

1. 键盘动作使用受控按键映射表。
2. 不接受原始内存码或任意 Win32 调用参数。
3. 运行程序使用电脑端批准目标，不直接执行手机传来的命令行。
4. 宏执行设置步骤数量和总时长限制。
5. 涉及关机、锁定、删除等危险动作必须二次确认或默认不提供。

### 15.4 日志

1. 默认日志不记录完整快速文字内容。
2. 默认日志不保存音频。
3. 错误日志不写入密钥、令牌或隐私文本。
4. 提供用户可理解的日志清理方式。

## 16. 性能与可靠性要求

### 16.1 快捷键

- 手机点击至电脑接收确认的正常目标：USB 下尽量小于 200 ms；
- 单次请求失败时允许有限重试；
- 重试不得导致同一动作重复执行；
- 组合键执行后不得残留 Ctrl、Alt、Shift 或 Win 按下状态。

### 16.2 主界面

- 100 个按钮配置仍可正常加载；
- 打开 App 不因配置解析阻塞明显时间；
- 拖动排序和滚动保持流畅；
- 设置保存失败时明确提示，不假装成功。

### 16.3 长期运行

- 手机屏幕开关后连接可恢复；
- USB 重新插拔后可通过启动脚本恢复；
- USB 共享切换器切换端口后，各电脑后台可自动恢复 ADB 转发；
- 局域网 IP 变化后可依靠电脑 ID 重新发现；
- 一台目标电脑离线不影响其他已配对电脑；
- Windows 接收端重复启动不会产生多个监听实例；
- 连续使用数小时不持续增长内存或线程；
- 蓝牙断开后可重连。

## 19. 已确认决策记录

以下事项已于 2026-08-26 确认采用推荐方案。若以后改变决定，应保留原记录并追加变更原因。

### D-01：按钮自定义范围

选择：

1. 只允许修改现有按钮；
2. 允许修改、隐藏和排序；
3. 允许修改、隐藏、排序、新增和删除自定义按钮。

决定：选择 3。内置按钮可以修改、隐藏、排序和恢复，但不能永久删除；自定义按钮允许删除。

### D-02：快捷键录入方式

选择：

1. 只在手机上使用按键选择器；
2. 在电脑上按一下真实快捷键，由 PhoneDeck 捕获；
3. 两种方式都提供。

决定：1.5.0 先实现手机按键选择器；电脑捕获放到 1.5.x 或 1.7.0。

### D-03：按钮图标（后续已变更）

选择：

1. 仅内置图标；
2. 内置图标加 Emoji；
3. 再允许从手机相册选择图片。

原决定：1.5.0 选择 2，使用内置图标加 Emoji。

2026-08-27 用户变更：快捷操作全部改为纯文字卡片，因原图标风格显得廉价且过度 AI 模板化。应用图标、语音麦克风和功能性状态图形继续保留。

### D-04：主界面列数

选择：

1. 固定 3 列；
2. 设置中选择 2、3、4 列；
3. 每个配置单独选择列数。

决定：1.5.0 固定 3 列，1.7.0 再支持每个配置独立列数。

### D-05：是否支持长按和双击动作

决定：1.5.0 普通按钮单击执行动作，长按进入该按钮编辑页，双击不绑定动作；语音按钮继续保留现有两种模式。长按进入编辑后必须消费本次触摸，松手不得误执行快捷键。

### D-06：配置主要保存在哪里

选择：

1. 只保存在手机；
2. 只保存在电脑；
3. 手机保存布局，电脑保存程序路径等机器相关目标，并做同步。

决定：1.5.0 采用 1，以手机本地配置为主；加入启动程序功能时升级为 3，由手机保存布局、电脑保存机器相关目标。

### D-07：是否允许启动程序和文件

决定：后续允许，但只能选择电脑端已经批准的目标；不允许手机发送任意命令行。

### D-08：是否需要前台软件自动切换配置

决定：需要，因多电脑功能提升优先级，顺延至 1.7.0，并提供手动锁定当前配置的能力。

### D-09：是否支持快速文字

决定：支持，但必须提示隐私风险，不建议存密码。

### D-10：是否支持剪贴板同步

决定：可以做，但默认关闭，且放在较后版本。

### D-11：是否提供危险系统动作

包括关机、重启、注销、锁屏等。

决定：锁屏可以考虑；关机、重启、注销和任意脚本默认不提供，除非后续加入明确确认机制。

### D-12：App 名称和定位是否调整

当前显示名是“手机键盘”，产品名是 PhoneDeck。

可选：

1. 继续显示“手机键盘”；
2. 改为“PhoneDeck”；
3. 改为“PhoneDeck 手机控制台”；
4. 使用其他中文名称。

决定：随 1.5.0 改为“PhoneDeck 手机控制台”，因为该版本上线后产品已不再只是固定的手机键盘。

### D-13：是否支持一台手机管理多台电脑

决定：支持，并提升为核心产品能力。目标为一台 Android 手机管理两至四台 Windows / macOS 电脑。

### D-14：多电脑动作发送范围

决定：快捷键、文字、宏和 `managed` 手机控制听写默认采用单一当前目标；用户显式选择并
手动开启 `shared` 共享麦克风时，只有 PCM 音频广播到所有合格电脑，Typeless 仍由各电脑
本机快捷键触发。共享运行状态不跨 App/手机重启恢复。

### D-15：多电脑连接是否强制使用局域网

决定状态：待硬件实测后最终确认。

当前推荐：采用混合架构。局域网或手机热点负责多台电脑同时在线和手机内一键切换；直接 USB 与多电脑 USB 共享切换器作为不使用局域网时的可选模式；蓝牙保留快捷键备用。

### D-16：USB 一分多硬件选择

决定：普通 USB Hub、Y 形数据线或被动一分三线不采用。允许研究支持三至四台主机的正规 `USB Peripheral Sharing Switch`，购买一台样机完成兼容验证后再列为正式支持硬件。

### D-17：语音进行中切换电脑

决定状态：采用受控交接作为推荐方案，进入 1.6.x 前最终确认细节。交接顺序为旧电脑停止、关闭旧音频、新电脑连接、建立新音频、新电脑启动；切换期间允许短暂停顿。

### D-18：macOS 多电脑兼容

决定：手机端采用统一设备模型；macOS 使用独立接收端和平台音频 / 输入后端，目标版本暂定 2.0。

2026-08-31 追加：项目所有者确认立即开始第三台 Mac 适配。先交付安全传输 + CGEvent 输入
预览并做混合三机验收，再接 Core Audio / BlackHole / Typeless；不让未完成音频阻塞第一轮
Mac 快捷键真机验证。

2026-09-03 追加：macOS 最低版本提升为 14.2；2.0.0-dev.2 已实现 AUHAL/BlackHole、
Typeless 动态配置和进程采集探针。共享模式在探针不可用时仍允许供音，managed 必须安全拒绝。

## 22. 当前建议结论

PhoneDeck 的近期基础仍是建立稳定、易用和安全的自定义按键系统；完成该基础后，下一项最高价值能力是一台手机管理多台电脑。

建议将 1.5.0 明确命名为：

> **PhoneDeck 1.5.0 — 可编程快捷键**

1.5.0 先把“修改按钮 → 选择 F1 → 测试 → 保存 → 主界面生效”做到可靠，同时把协议设计成支持电脑身份和平台能力。1.6.0 随后实现“选择电脑 → 状态确认 → 语音或快捷键只进入该电脑”的核心链路。

普通 USB 一分多不能完成多主机连接。正规 USB 共享切换器能够提供无需局域网的物理切换模式，但只有一台电脑在任意时刻真正连接手机。若最终目标是三台电脑同时在线、由手机直接选择目标，局域网或手机热点仍然是主方案。PhoneDeck 因此采用传输层可替换的混合设计，不把未来能力锁死在任何一种连接方式上。
